# NORTHIA

Мобильный магазин предзаказа по пятиэтапному ТЗ. Next.js 16.4.3, React 19.3, TypeScript, Tailwind v4; без UI-библиотек и онлайн-оплаты. Дополнительные runtime-зависимости: zod и googleapis.

## Запуск

Рекомендуется Node.js 24 (проект проверен на 24.21.0), npm 11.

```powershell
cd Z:\northia
npm ci
npm run dev -- --hostname 127.0.0.1 --port 5000
```

Откройте http://127.0.0.1:5000; админ-панель — http://127.0.0.1:5000/admin. Для production-сборки:

```powershell
npm run check
npm start
```

Предзаказ отправляется сервером в существующий Google Apps Script. Без настройки Google API возвращает ошибку и сохраняет данные формы; ложный успех и вывод персональных данных в development отключены.

## Настройка Google Apps Script

Существующая форма → POST /api/preorder → серверная валидация и каталог → POST JSON в Apps Script. Дизайн и клиентские имена полей сохранены. Настройки доступны только серверу, без NEXT_PUBLIC_:

| Переменная | Значение |
| --- | --- |
| GOOGLE_SCRIPT_URL | URL существующего развёртывания Apps Script с окончанием /exec |
| GOOGLE_SCRIPT_SECRET | Предоставленный владельцем секрет, передаётся в JSON-поле secret |

Локально значения заданы в игнорируемом .env.local. На хостинге добавьте их в переменные окружения и перезапустите приложение. Секрет не помещается в Git, README или клиентский JavaScript.

Сервер отправляет fullName (поле name формы), phone, contact, city, pickupAddress (поле address), comment и secret. В comment сохраняются комментарий покупателя, ID заявки, товары, размеры, цвета, количество, серверные цены и итог через formatPrice. Цены клиента не используются.

Ожидаемая структура таблицы A:H: Дата | ФИО | Телефон | Контакт | Город | Адрес пункта выдачи | Комментарий | Статус. Дату и статус «Новая» устанавливает существующий Apps Script; сайт их не передаёт.

Ответ скрипта должен быть JSON с явным подтверждением записи: {"ok":true}, {"success":true} или {"status":"success"}. Явный отказ, поле error, противоречивые статусы, HTML, пустой/невалидный JSON и HTTP-ошибка считаются неуспехом. Точный контракт существующего скрипта и реальные значения A/H требуют проверки в Google: исходник скрипта не предоставлен, запись в рабочую таблицу в этой задаче не выполнялась.

Fetch следует редиректу ContentService согласно [документации Google](https://developers.google.com/apps-script/guides/content#redirects). Таймаут — 15 секунд; автоматических повторов нет. После подтверждения форма показывает существующий экран успеха и очищает корзину; при ошибке сохраняет поля и корзину.

Лист ожидания сохраняет прежнюю отдельную интеграцию: GOOGLE_SERVICE_ACCOUNT_EMAIL, GOOGLE_PRIVATE_KEY и GOOGLE_SHEET_ID, вкладка «Лист ожидания» A:C (Дата | Имя | Контакт). Apps Script с контрактом предзаказа для него не вызывается. Без его настроек показывается ошибка, персональные данные не выводятся в консоль. Для предзаказов сервисный аккаунт больше не нужен.

## Защита и ограничения

- Клиент и сервер проверяют обязательные поля, trim и лимиты; телефон допускает цифры, пробелы, +, скобки и дефисы, от 7 до 15 цифр.
- JSON-тело ограничено 32 KiB; позиции 1–50, количество 1–99. Неизвестные товары, недоступные размеры и дубли slug+size отклоняются.
- Названия, цены, цвета и итог считаются по серверному каталогу. Посторонние поля клиента отбрасываются.
- Заполненный honeypot website возвращает ok без записи и логирования заявки.
- Rate limit: 10 запросов за 10 минут на IP и тип формы, HTTP 429 с Retry-After; до 10 000 ключей в памяти.
- **Rate limit в serverless ограничен одним процессом**, сбрасывается при перезапуске и не синхронизируется между инстансами. Хостинг должен перезаписывать x-vercel-forwarded-for/x-forwarded-for; иначе IP можно подделать. Для публичной нагрузки нужен доверенный proxy и распределённый limiter/WAF.
- Прямая интеграция листа ожидания экранирует формулы и использует RAW. Для предзаказов корректную текстовую запись ячеек должен обеспечивать существующий Apps Script.
- В production логируются только безопасные коды ошибок; объект Google error, заголовки запросов и ключи не выводятся.
- У Apps Script таймаут 15 секунд, у прямого Sheets API — 10 секунд, автоматические повторы отключены. Нет гарантии exactly-once при потере ответа после успешного append: повторная отправка может создать дубль. Для такого требования понадобится долговечное хранилище ключей идемпотентности.
- При ошибках 400/429/500 и сети поля и корзина остаются; очистка только после успеха. Кнопка блокируется во время запроса, повторный submit отклоняется синхронным флагом.

## Админ-панель

Вход: /admin, данные доступа заданы владельцем и уже настроены локально. Пароль не хранится в исходном коде: storage/admin.json содержит соль и scrypt-хеш. Сессия длится 8 часов; HttpOnly/SameSite=Strict, Secure при HTTPS, выход аннулирует серверную сессию. Лимит входа — 5 попыток в минуту на один серверный процесс.

Товары: добавить, изменить цену/размеры/цвет/тип/срок отправки/описание/доставку/уход, загрузить фотографии, изменить порядок и скрыть. Новые товары сначала скрыты; включите «Показывать на сайте» и нажмите «Сохранить изменения». Адрес сохранённого товара закреплён. Первая фотография — обложка; можно менять порядок и убирать кадры из товара. Файлы при этом остаются на диске для сохранности ссылок.

Контент: главное изображение и подпись, alt, текст бренда, заголовок каталога, изображение/текст новой коллекции, тексты предзаказа и листа ожидания, контакты и юридическое имя. Тексты — обычный текст с переносами строк; HTML не исполняется. Фотографии: JPEG/PNG/WebP до 8 МБ, до 12 кадров товара.

Сохранение атомарное, с проверкой версии: устаревшая вкладка не перезапишет свежие изменения. Каталог, карточки, корзина и серверный расчёт заявки получают рабочие товары. Скрытые товары и недоступные размеры не принимаются сервером. После сохранения уже открытые страницы магазина нужно обновить.

На новом окружении первичная настройка: передайте ADMIN_SETUP_LOGIN и ADMIN_SETUP_PASSWORD через защищённое окружение процесса и выполните npm run admin:setup; существующий аккаунт скрипт не перезаписывает. Не коммитьте и не выводите storage/admin.json или файлы сессий.

Проверка админки: передайте TEST_ADMIN_LOGIN, TEST_ADMIN_PASSWORD и при необходимости TEST_BASE_URL в окружение, выполните npm run test:admin. Только на локальной тестовой копии: тест меняет контент и восстанавливает его в finally, оставляя тестовый медиафайл на диске.

## Supabase / PostgreSQL 17 (новый основной режим)

Этот раздел описывает новый режим и имеет приоритет над прежними разделами Google для него. Для сертификата Supabase при необходимости задайте DATABASE_SSL_CA (PEM, литеральные \n поддерживаются); проверка сертификатов не отключается. Не добавляйте sslmode/sslcert/sslkey в URL: используйте отдельную настройку CA. Драйвер pg выбран из-за ограничений pipeline Postgres.js на shared transaction pooler. Если DATABASE_URL отсутствует, локальная файловая/Google-конфигурация остаётся доступна для тестирования. Если DATABASE_URL задан, каталог, настройки, история редакций, заявки, лист ожидания, версии/время согласий, администраторы, сессии и лимиты запросов используют PostgreSQL; при сбое БД приложение не переключается на файлы или Google. Браузерная корзина остаётся в localStorage.

Переменные только на сервере (не NEXT_PUBLIC): DATABASE_URL, SUPABASE_URL (https://<project>.supabase.co), SUPABASE_SERVICE_ROLE_KEY. Не публикуйте пароль БД и service role key. Для предоставленного pooler используйте строку из Connect с реальным URL-encoded паролем. Приложение использует TLS с проверкой сертификата, один connection на экземпляр и параметризованные запросы без именованных prepared statements (драйвер pg). Проверка версии требует PostgreSQL 17.x; она выполняется скриптом db:check до миграции.

Схема db/001_initial.sql: закрытая northia с девятью таблицами, RLS и без доступа anon/authenticated; записи выполняются сервером. Каталог хранит каждый товар отдельной строкой JSONB с порядком; настройки — отдельной записью с revision. Сохранение каталога и истории атомарно, устаревшая revision даёт CONFLICT. Заказ сохраняет серверные цены/состав в транзакции, независимо от будущих изменений товара. Клиентские цены не принимаются.

Изображения: закрытый bucket northia-media в Supabase Storage; в PostgreSQL — имя/MIME/размер. Старые URL /media/<uuid> сохранены, выдача идёт через сервер. Bucket ограничен JPEG/PNG/WebP до 8 МБ. SUPABASE_SERVICE_ROLE_KEY имеет широкие права — доступен только серверу. Не использовать личные/закрытые документы в bucket: фотографии, доступные на сайте, выдаются публичным маршрутом /media. Пара загрузка объекта/запись метаданных не является общей транзакцией; при сбое после загрузки возможен неиспользуемый объект. Автоматического удаления объектов нет.

### Подключение и перенос (после одобрения внешних изменений)

1. Сохраните переменные в игнорируемом .env.local; остановите редактирование контента на время импорта. Сделайте собственную резервную копию storage. Удалённый проект должен быть предназначен для NORTHIA.
2. `npm run db:check` — безопасная проверка подключения и версии, без записи.
3. `npm run db:migrate -- --apply` — создаёт схему/таблицы и закрытый bucket, существующие строки не удаляет. Выполняет REVOKE/RLS для выделенной схемы; не применять к схеме, используемой другим приложением. Существующий bucket с тем же именем не перенастраивается — проверьте его private-режим и ограничения.
4. `npm run db:media -- --apply` — копирует локальные storage/media в Storage и регистрирует метаданные. Не перезаписывает существующие объекты. При частичном сбое с уже загруженным объектом нужна ручная сверка объекта и метаданных; повтор не удаляет данные.
5. `npm run db:import -- --apply` — проверяет contentSchema, атомарно импортирует storage/content.json и существующий хеш администратора (если есть). Повторный импорт в инициализированный каталог запрещён; файлы остаются на месте. Старые сессии не переносятся. При отсутствии локального администратора: ADMIN_SETUP_LOGIN/ADMIN_SETUP_PASSWORD через защищённое окружение и `npm run db:admin -- --apply` (существующая учётная запись не меняется). `npm run admin:setup` также выбирает БД при DATABASE_URL.
6. Перезапустите сайт. Проверьте каталог/админку/фото и тестовые заявки в таблицах orders/waitlist. Старые Google-заявки автоматически не импортируются. Новые запросы в DB-режиме не отправляются в Google.

Миграция/импорт/настройка администратора выполняют внешние записи — команды подготовлены, но агент их не запускал. До запуска отсутствуют DATABASE_URL, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY. Для отката к тестовой локальной конфигурации уберите DATABASE_URL и перезапустите процесс; новые изменения в БД автоматически в файлы не возвращаются. Автоматической обратной миграции и удаления удалённых таблиц нет.

Проверки: `npm run test:db` использует изолированный PGlite PostgreSQL-движок для миграции/приватности/ограничений/снимков цен, а также реальных функций чтения/сохранения каталога, отката конфликтов, параметризации, записи заказов и листа ожидания, без сети. Это не проверка реального Supabase, TLS, pooler, Storage и конкурентных запросов. `npm run test:unit` проверяет прежний канал с подменённым fetch. Docker установлен, но daemon недоступен — отдельный сервер PostgreSQL локально не запускался.

Перед реальными заказами: регион eu-west-1 не является размещением базы в России; остаются вопросы локализации/уведомлений и окончательной политики. Включите резервное копирование и проверьте восстановление на выбранном тарифе. Автоматическая очистка истории контента и завершённых заказов по политике хранения пока не настроена. Просмотр заказов пока через закрытые серверные таблицы, отдельный интерфейс управления заказами не добавлялся.

## Ошибка SELF_SIGNED_CERT_IN_CHAIN

В Supabase откройте Database Settings → SSL Configuration → Download Certificate. Добавьте полное содержимое PEM (включая BEGIN/END CERTIFICATE) в DATABASE_SSL_CA в Vercel для нужного окружения. Допускаются настоящие переводы строк или литеральные \n; кавычки вокруг значения в интерфейсе Vercel не нужны. После настройки и публикации исправления создайте новый deployment.

Приложение и migration CLI используют единый database-ssl.ts: сертификат разбирается до подключения, TLS/проверка сертификата остаются включёнными. SSL-параметры URI удаляются из копии URL, чтобы pg не заменял явные CA/verify-настройки; остальные параметры сохранены. Оригинальная переменная не меняется. Не используйте NODE_TLS_REJECT_UNAUTHORIZED=0. Сертификат CA публичный, пароль БД/service role key передавать в чат не нужно. Реальное подключение подтверждается отдельно через npm run db:check после настройки окружения.

## Логин и пароль администратора через Vercel

Задайте серверные переменные ADMIN_LOGIN (например, Vikt_246) и ADMIN_PASSWORD (12–256 символов) для Production. Обе обязательны для режима override; пароль не обрезается и не нормализуется. Включите Sensitive для пароля, не используйте NEXT_PUBLIC_. После изменения создайте новый deployment. ADMIN_SETUP_* нужны только скриптам создания учётной записи и не управляют текущим входом.

При заданных ADMIN_LOGIN/ADMIN_PASSWORD учётная запись из окружения является единственной для входа: пароль БД/локального файла не принимается. Если обе переменные отсутствуют, действует прежний вход через БД/файл. Частичная или некорректная настройка отклоняется без fallback. Пустые значения не заменяют отсутствие переменных — удалите обе переменные для возврата прежнего режима.

При создании сессии её хеш привязывается к текущим credentials через HMAC; после смены любого значения старые сессии не проходят проверку на новом deployment. После удаления override прежние сессии режима БД/файла могут оставаться действительными до их 8-часового срока — для полного отзыва всех исторических сессий нужна отдельная очистка. Старые deployments используют своё окружение, ограничьте доступ к ним средствами хостинга при необходимости. Пароль не записывается приложением в БД/файлы и не отправляется клиенту. Хранение сессий и лимитов остаётся в PostgreSQL при DATABASE_URL, поэтому схема должна быть инициализирована; override не отменяет миграцию.

## Формат новых изображений

Новые загрузки через админку принимаются только в PNG до 8 МБ. Сервер проверяет PNG-сигнатуру и сохраняет исходные байты без перекодирования, с расширением .png и MIME image/png; прозрачность не меняется. Это относится к главной, коллекции и товарам. JPEG/WebP нужно заранее экспортировать в PNG. Старые JPEG/WebP и SVG-заглушки продолжают обслуживаться; автоматической конвертации старых файлов и изменения удалённого bucket не выполнялось. Next/Image может выдавать оптимизированную копию в другом формате для браузера — формат оригинала в Storage остаётся PNG.

## Лимит загрузки на Vercel — актуализация

Текущий лимит загрузчика — 4 МБ (4 194 304 байта), он заменяет прежние указания 8 МБ для новых загрузок через админку. Проверяется до fetch и на сервере. Причина: лимит тела Vercel Function 4,5 МБ. Ответы 413/401/403 и не-JSON ошибки хостинга обрабатываются понятным сообщением; выбранное изображение меняется только при подтверждённом /media/*.png. Для PNG больше 4 МБ требуется предварительно уменьшить размер файла; загрузка больших оригиналов напрямую в Storage пока не реализована. Ограничение bucket 8 МБ сохранено для совместимости с прежними объектами и импортом.

## Актуально: заявки только в Google Sheets — 28 октября 2026

Этот раздел заменяет прежнее описание сохранения заявок в DB-режиме. Предзаказы всегда отправляются через GOOGLE_SCRIPT_URL/GOOGLE_SCRIPT_SECRET в существующий Apps Script. Лист ожидания всегда записывается через GOOGLE_SERVICE_ACCOUNT_EMAIL/GOOGLE_PRIVATE_KEY/GOOGLE_SHEET_ID во вкладку «Лист ожидания»: A дата, B имя, C контакт, D версия/время согласия. Для обоих каналов нужны свои переменные в Vercel даже при наличии DATABASE_URL. Отсутствие настроек или ошибка Google дают ошибку формы, без ложного успеха и без fallback в PostgreSQL.

Каталог, настройки, медиа, администраторы, сессии и технические rate limits продолжают использовать Supabase при DATABASE_URL. Контактные данные, состав и согласие новых заявок не записываются в northia.orders/northia.waitlist. Эти исторические таблицы и старые записи не удалялись; автоматического переноса прежних заявок в Google нет. Серверная проверка товаров/цен и согласия сохранена; каталог читается из текущего хранилища. Действует прежний лимит Apps Script 2000 символов для сформированного комментария вместе с составом заказа.

## Диагностика Google Sheets 403

В безопасный серверный лог добавлены stage (metadata: получение списка вкладок, append: запись строки) и googleReason. Выводятся только известные коды Google: SERVICE_DISABLED/accessNotConfigured (настройка API), forbidden/PERMISSION_DENIED (права), ACCESS_TOKEN_SCOPE_INSUFFICIENT (scope), quota/rate-коды (лимиты). Неизвестные строки заменяются unclassified; тела ответов, сообщения Google, request/response headers, ключи и контактные данные не логируются. Пользователю формы остаётся общее сообщение. После публикации диагностики нужен свежий лог для определения конкретной причины; 403 сам по себе её не устанавливает. Предоставленный владельцем Apps Script обрабатывает только «Заявки» и не заменяет отдельную интеграцию листа ожидания.

## Актуально: обе формы через единый Apps Script

Предзаказ и лист ожидания теперь используют одни GOOGLE_SCRIPT_URL и GOOGLE_SCRIPT_SECRET. Отдельные GOOGLE_SERVICE_ACCOUNT_EMAIL/GOOGLE_PRIVATE_KEY/GOOGLE_SHEET_ID для форм больше не требуются. Не удаляйте эти переменные, если они нужны другим приложениям; сайт их для новых заявок не использует.

Контракт waitlist: сервер отправляет type="waitlist", name, contact, consentVersion и secret. Обновлённый Код.gs должен обрабатывать эту ветку до проверки обязательных полей предзаказа и писать A:D во вкладку «Лист ожидания» (дата, имя, контакт, версия согласия/время получения). Перед запуском сайта нужно обновить развёртывание Apps Script версией с поддержкой waitlist, сохранить FORM_SECRET и создать вкладку. Без этого старый скрипт вернёт Invalid fields. Контракт обычных заявок без type не изменён.

Транспорт общий: серверный secret, ограничение URL /exec, таймаут 15 секунд, отсутствие автоматических повторов, проверка явного JSON-успеха. Поддельный клиентский type/secret не пересылается; payload формируется сервером после валидации согласия. В PostgreSQL новые заявки не записываются. Реальное развёртывание Apps Script этим изменением не менялось и строки в Google не добавлялись.

## Проверка опубликованной версии Apps Script

Канонический полный исходник теперь scripts/google-apps-script.gs. Замените им Код.gs целиком и обновите версию существующего deployment. Добавлен публичный doGet без данных таблицы/секрета: при открытии точного GOOGLE_SCRIPT_URL /exec в браузере возвращается {success:true,supportsWaitlist:true,version:"northia-2026-10-28-waitlist-v1"}. Если метки нет или doGet не найден, по этому адресу опубликован другой код. Если метка есть, сравните URL с GOOGLE_SCRIPT_URL окружения Production и проверьте актуальный deployment сайта.

Изолированный контрактный тест связывает настоящий submit/sendScriptWaitlist с выполнением этого файла через VM, заменяя Google-сервисы памятью: лист ожидания пишет A:D, обычный заказ A:H, неверные поля не пишутся, проверяется версия GET. Это подтверждает совместимость кода, но не состояние развёртывания Google. Для проверки GET не отправляйте FORM_SECRET в URL.
